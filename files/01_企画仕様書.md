# RailAngyer 企画・仕様書

> **RailAngyer（レイルアンギャー）** — サイコロで駅を巡る徒歩すごろくアプリ
> 「鉄道（Rail）」×「行脚（あんぎゃ）」。歩いて駅を巡ることを名前にした。
> 作成日: 2026-07-25 / 対象: 身内向け / 収益: 非重視
> Azure リソース名: `RailAngyer` / `railangyer` ／ リポジトリ: `non-migi/RailAngyer`

---

## 1. コンセプト

実際に地下鉄・鉄道の駅を「歩いて」巡り、サイコロとミッションで双六のように遊ぶ、身内向けのiOSアプリ。

まず札幌市営地下鉄・南北線（全16駅）から始め、将来的に東西線・東豊線、山手線一周、その他のエリア・路線へ「盤面（コース）」を追加していく拡張前提の設計とする。

### 一言で

「歩いて巡る × サイコロすごろく × 身内で共有できるミッション」

---

## 2. コアループ（遊びの流れ）

チーム全体で **1つのコマ** を進める。**サイコロの目 = 進む駅数**。

1. 始点の駅（例: 麻生）に集合し、**サイコロを振る**
2. 出た目 N の数だけ先の駅を目指して歩く
3. **途中の N-1 駅も、1駅ずつ実際に到達して訪れる**（素通りではない）。各駅で写真を撮れるなら撮る
4. N駅先の**着地駅**に到着（GPSで到着判定）。ここでも写真を撮る
5. 着地駅に用意されたミッション群から**ランダムに1つ**選ばれ、それを行う
6. ミッションを達成したら、その場で再び**サイコロを振る** → 2 に戻る
7. ゴール駅（例: 真駒内）に到達したらクリア。写真・記録をまとめて身内に共有

### ルール補足
- **サイコロは移動そのもの**（何駅進むか）を決める。目に難易度などの意味は持たせない。
- **ミッションは着地駅でのみ行う**。途中で訪れた駅では行わない（訪問記録と写真だけ残る）。
- **出目がゴールまでの残り駅数を超えても、そのままゴール**とする（ぴったり止まる必要はない）。
- 既定（最大出目6・16駅）なら平均3.5駅進むため、ミッションの実施は **5回前後**。

### 可変ルール（ルームごとに設定）
同じ路線でも、ルームを作るときの設定で遊び方を変えられる。

- **区間**: スタート駅とゴール駅を**コース内の任意の駅から選べる**。一部区間だけ遊ぶことも、逆方向に進むこともできる。
- **最大出目**: サイコロを **1〜9 の範囲で設定**できる（既定6）。1にすると毎ターン必ず1駅ずつ進み、区間の全駅でミッションを行うことになる。

### ミッションの効果
ミッションには、お題に加えて**コマを動かす効果**を付けられる（効果なしが既定）。

| 効果 | 内容 |
|---|---|
| なし | 通常のお題。コマは動かない |
| 進む N駅 | ゴール方向へ N駅進む。ゴールは超えない |
| 戻る N駅 | スタート方向へ N駅戻る。スタートより手前へは行かない |
| もう一度振る | 位置はそのままで、すぐ次のサイコロを振る |
| 指定駅へ移動 | 区間内の指定した駅へ移動する（前でも後ろでもよい） |

- 効果による移動でも、**途中の駅は歩いて訪れる**。
- **効果で移動した先ではミッションを引かない**（連鎖して止まらなくなるのを防ぐため）。
- 戻る・ジャンプにより、**同じ駅を複数回訪れることがある**。訪問記録はそのつど残る。

### 例
麻生スタート → 「3」→ 北34条・北24条を訪れつつ北18条に着地 → 北18条のミッションを実施 → 達成 → 「2」→ 北12条を訪れつつさっぽろに着地 → …

## 3. 主な機能

### 3.1 プレイ機能
- **サイコロ**: 振った目の数だけ駅を進む。振るのはスタート時とミッション達成時
- **駅到着判定**: GPSで駅の半径150m以内に入ったら到着とみなす（半径は調整可能）。**通過する駅も含め、訪れたすべての駅で判定・記録する**
- **写真撮影**: 訪れた駅で撮れるなら撮る。駅・撮影者に紐づけて保存（着地駅・途中駅とも可）
- **ミッション抽選**: **着地駅**に紐づくミッション群から、クライアント側でランダムに1つ選ぶ
- **道案内（ナビ）**: 次の駅までの徒歩ルートを地図で表示
- **すごろく盤 / 路線図**: 訪問済み駅が塗られていく。着地駅（ミッション実施駅）は区別して表示。達成率を表示

### 3.2 ミッション機能
- **ミッションの自作**: プレイ前の準備フェーズで、各メンバーがミッションを作る
- **駅ごとに作る**: 各メンバーは、**駅ごとに1つ、または0個**ミッションを用意する
  （例: 4人チームなら、1つの駅につき最大4個のミッションが集まる。誰も作らなければ0個）
- **駅ごとのプール**: その駅に集まったミッションから、着地時にランダムで1つ抽選される

### 3.3 共有・計画機能
- **ミッションセットの共有**: 複数の身内が同じミッションセット（ルーム）を共有
- **予定（スケジュール）**: プレイ日時・集合場所を立てて、メンバー間で共有・参加可否を表明
- **記録の共有**: 誰がどの駅にいつ着いたか、撮った写真を共有

### 3.4 閲覧・振り返り
- すごろく盤で全体の進捗を見る
- 達成率を確認する
- 駅の詳細（到着日時・ミッション結果・写真）を見返す
- 記録をリセットして再挑戦

## 6. なぜ共有DB（サーバー側）が必要か

以下の3要件は、いずれも「ある端末で作ったデータを別の端末が読む」動作であり、端末内ローカル保存（SwiftData / UserDefaults）だけでは実現できない。

1. 複数の身内が同じミッションセットを共有する
2. 予定を立てて共有する
3. 各メンバーが駅ごとに出したミッションを1つのプールにまとめ、着地駅でそこから抽選する

このため、みんなのデータが集まる共有の置き場所 = サーバー側DBが必要になる。
本ドキュメントでは、本業スタックと親和性の高い **Azure SQL Database** を採用する前提で設計する（詳細は別ファイル参照）。

## 7. 決定事項 / 要確定事項

### 決定済み

- [x] **サイコロの目の意味**: **進む駅数**。難易度などの意味は持たせない。
- [x] **ミッションの割り当て単位**: **駅ごと**。各メンバーが駅ごとに1つ、または0個を用意する。
- [x] **コマの単位**: **チーム全体で1つのコマ**を進める（個人ごとに駒は持たない）。
- [x] **ゴール時の出目超過**: 残り駅数を超える目が出ても、**そのままゴール**とする。
- [x] **途中駅の扱い**: 通過する駅も**実際に到達して訪れる**。写真は撮れるなら撮る。ミッションは着地駅のみ。
- [x] **始点・ゴール**: **ルームごとに任意の駅を選べる**（一部区間・逆方向も可）。固定しない。
- [x] **クリア条件**: 設定したゴール駅への到達。
- [x] **サイコロの最大出目**: **ルームごとに 1〜9 で設定**（既定6）。
- [x] **ミッションの効果**: 進む／戻る／もう一度振る／指定駅へ移動 を付けられる。

### 未確定

- [ ] **着地駅にミッションが0個だった場合の挙動**: 誰もその駅のミッションを作らなかったとき、
      ①ミッションなしで即サイコロを振る／②予備の共通ミッションから出す／③1駅ずらす、など。
      **暫定は①**。
- [ ] **効果の発動条件**: ミッションの達成・未達成にかかわらず発動するか、達成したときだけか。
      **暫定は「達成の可否にかかわらず発動」**。
- [ ] **「もう一度振る」の連鎖上限**: 連続で発動しうるため上限が要る。**暫定3回**。
- [ ] **再訪時のミッション**: 戻る効果で同じ駅に再度着地したとき、既に引いたお題を除外するか。**暫定は除外**。
- [ ] **効果を書ける人・数の制限**: 全員が「戻る」を書くと進まなくなる。制限するか、準備画面で可視化するだけか。
- [ ] **写真の必須度**: 着地駅では必須にするか、全駅とも任意か。
- [ ] **メンバー識別方式**: 招待コードか、メールのマジックリンクか（認証の軽さ）。
- [ ] **同時プレイ**: チームで1コマのため全員一緒に歩く前提だが、遅れて合流・途中離脱を許すか。
