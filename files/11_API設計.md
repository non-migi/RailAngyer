## 1. 方針

| ID | 方針 | 理由 |
|---|---|---|
| AP-01 | **ASP.NET Core Web API を App Service F1（無料）に置く** | 本業スタックそのままで学習コストが要らない。F1 は常時無料で、CPU 60分/日は身内数人の利用では使い切らない |
| AP-02 | **APIはできるだけ薄く。判断はクライアントに置く** | 抽選も位置判定もアプリ側で済んでいる。APIは「保存する・配る」だけにする |
| AP-03 | **すべての書き込みを冪等にする** | オフラインで溜めた要求を再送しても二重登録しないため（G-7） |
| AP-04 | **写真の実体はAPIを通さない** | App Service F1 の帯域とCPUを食う。SASでBlobへ直接上げる（G-6） |
| AP-05 | **リクエストの `MemberId` を信用しない** | 誰でも他人になりすませてしまう。トークンから解決する（G-5） |

### コールドスタートを前提にする

App Service F1 は約20分でスリープし、Azure SQL も自動一時停止する。
**両方が寝ていると最初のリクエストに1分近くかかる。**

- クライアントのタイムアウトは **60秒以上**にする
- 失敗しても**プレイは止めない**。ローカルを正として、後から送る（`CM-04` / `E-03`）
- 起動時に「起こすためだけ」の軽い `GET /health` を投げておくと、実プレイ時の待ちが減る

## 2. 認証 ── なりすまし対策（G-5）

### 何が問題だったか

これまでの設計は「招待コードでルームに参加し、`MemberId` を端末に保持する」だけだった。
APIから見ると、**リクエストに書かれた `MemberId` が本人のものか確かめる手段がない**。
身内でも「他人の名前でミッションを書く」「他人の写真を消す」ができてしまう。

### 方式：メンバートークン

参加時にサーバーがトークンを発行し、以降のリクエストに付ける。

```
POST /rooms/join            → { memberId, token }
Authorization: Bearer <token>   （以降すべて）
```

| 項目 | 仕様 |
|---|---|
| トークン | 32バイトの乱数を Base64URL で表現（43文字） |
| 保存 | **SHA-256 のハッシュだけをDBに保存**。平文は端末のキーチェーンにのみ置く |
| 有効期限 | 設けない。身内用のため。漏れたらメンバーを作り直す |
| 解決 | サーバーはトークンから `MemberId` と `MissionSetId` を引く。**リクエストボディの `MemberId` は無視する** |

### テーブルの追加

```sql
ALTER TABLE dbo.Member ADD TokenHash BINARY(32) NULL;
CREATE UNIQUE INDEX UX_Member_TokenHash ON dbo.Member(TokenHash) WHERE TokenHash IS NOT NULL;
```

### 招待コードの扱い

- 参加時にだけ使う。以降は使わない
- **ルーム作成者が無効化・再発行できるようにする**（漏れたときの手当て）
- 招待コードだけでは何も読めない。参加してトークンを得て初めてアクセスできる

> 身内用に厳密すぎるように見えるが、**トークン方式にしても実装量はほとんど増えない**。
> 参加時に1回発行し、以降はヘッダを見るだけで済む。

## 3. エンドポイント

すべて `Content-Type: application/json`。パスの `{roomId}` は省略できる（トークンから解決するため）が、
取り違えを検知するために付ける。

### 3.1 参加・ルーム

| メソッド | パス | 内容 | 認証 |
|---|---|---|---|
| `GET` | `/health` | 起こすためだけの応答 | 不要 |
| `GET` | `/courses` | コースと駅マスタ | 不要 |
| `POST` | `/rooms` | ルーム作成（作成者のメンバーも同時に作る） | 不要 |
| `POST` | `/rooms/join` | 招待コードで参加 | 不要 |
| `GET` | `/rooms/{roomId}` | ルームの設定とメンバー一覧 | 要 |
| `PATCH` | `/rooms/{roomId}` | 区間・最大出目の変更（**ターンが1件でもあれば 409**） | 要 |

```jsonc
// POST /rooms
{ "courseId": 1, "name": "夏の南北線ツアー",
  "startStationId": 1, "goalStationId": 16, "diceMax": 6,
  "displayName": "のん" }
→ 201
{ "roomId": "…", "inviteCode": "ABC123",
  "memberId": "…", "token": "…" }

// POST /rooms/join
{ "inviteCode": "ABC123", "displayName": "ケンタ" }
→ 200 { "roomId": "…", "memberId": "…", "token": "…" }
→ 409 表示名が重複（UQ-04）
```

### 3.2 ミッション

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/rooms/{roomId}/missions` | **自分のぶんだけ**返す（他人のお題は伏せる） |
| `PUT` | `/rooms/{roomId}/missions/{missionId}` | 作成・更新（冪等） |
| `DELETE` | `/rooms/{roomId}/missions/{missionId}` | 削除 |
| `GET` | `/rooms/{roomId}/missions/summary` | 駅ごとの件数と効果の内訳（**内容は返さない**） |
| `GET` | `/rooms/{roomId}/stations/{stationId}/missions` | **着地したときだけ**その駅の全ミッションを返す |

> **他人のお題を伏せるのはAPIの責務にする。** クライアントで隠すだけでは、
> 通信を覗けば見えてしまい、当日の驚きが失われる。

`/stations/{stationId}/missions` はサーバー側で「いまその駅に着地しているか」を確認してから返す。
確認できなければ 403。これで**先読みして全ミッションを覗くことを防げる**。

### 3.3 進行

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/rooms/{roomId}/state` | 現在位置・進行中ターン・訪問済み駅（復帰と同期の起点） |
| `PUT` | `/rooms/{roomId}/turns/{turnId}` | ターンの作成・更新（冪等）。`turnId` は**クライアントが生成** |
| `PUT` | `/rooms/{roomId}/visits/{visitId}` | 訪問の記録（冪等） |
| `DELETE` | `/rooms/{roomId}/progress` | 記録リセット（Turn と Visit と写真） |

```jsonc
// PUT /rooms/{roomId}/turns/{turnId}   サイコロを振った直後
{ "diceValue": 3, "fromStationId": 6, "landingStationId": 9,
  "rolledAt": "2026-07-30T05:22:11Z" }
→ 200 { "turnNo": 4, ... }        // TurnNo はサーバーが採番して返す
→ 409 { "error": "turn_in_progress" }   // 他の端末が振っている最中

// PUT ... 着地・ミッション・効果のたびに同じURLへ差分を送る
{ "arrivedAt": "…", "selectedMissionId": "…", "missionDone": true,
  "appliedEffectType": 2, "endStationId": 7, "completedAt": "…" }
```

### 3.4 写真・予定

| メソッド | パス | 内容 |
|---|---|---|
| `POST` | `/rooms/{roomId}/photos/upload-url` | **書き込み用SASを発行**（§5） |
| `PUT` | `/rooms/{roomId}/photos/{photoId}` | 写真メタの登録（アップロード完了後） |
| `GET` | `/rooms/{roomId}/photos` | 一覧。**読み取り用SAS付きのURL**を返す |
| `DELETE` | `/rooms/{roomId}/photos/{photoId}` | 削除（**撮影者本人のみ**） |
| `GET` | `/rooms/{roomId}/schedules` | 予定と出欠の一覧 |
| `PUT` | `/rooms/{roomId}/schedules/{scheduleId}` | 予定の作成・更新（**立てた人だけ**） |
| `DELETE` | `/rooms/{roomId}/schedules/{scheduleId}` | 予定の削除（**立てた人だけ**） |
| `PUT` | `/rooms/{roomId}/schedules/{scheduleId}/attendance` | 出欠を答える（**自分のぶんだけ**） |

## 4. 同期と冪等性（G-7）

### 何が問題だったか

`Turn.TurnNo` は連番。オフラインで振ったターンを後から送ると、
**別の端末が採番した番号と衝突する**（`UQ_Turn_No` 違反）。

### 解決：順序は時刻で決め、TurnNo は表示用にする

現在位置の導出は「最後に完了したターンの終了位置」だが、
**「最後」を `TurnNo` ではなく `RolledAt`（クライアントが振った時刻）で決める**ようにすれば、
`TurnNo` が衝突しても実害がなくなる。

| 用途 | 使う値 |
|---|---|
| 現在位置の判定・順序 | **`RolledAt`**（クライアント時刻、UTC） |
| 画面に出す「3ターン目」 | `TurnNo`（サーバーが受信順に採番） |

> クライアント時刻は信用できないが、**同じチームが1つのコマを動かす**用途では
> 端末間の時刻ずれより通信の遅れのほうが大きい。厳密な順序が要る場面ではない。

### 冪等性

- **主キーはクライアントが生成した UUID**（`turnId` / `visitId` / `photoId` / `missionId`）
- 書き込みはすべて `PUT`。既にあれば更新、なければ作成
- 再送しても二重にならないので、オフラインのキューを**素朴に再送するだけでよい**

### 送信キュー

```
プレイ中の操作 → ローカルに保存（これが正）
              → 送信キューに積む
              → オンラインになったら古い順に PUT
              → 失敗したら残す（次の機会に再送）
```

- **プレイはキューの状態に依存しない**。送れていなくても最後まで遊べる
- 未送信の件数は設定画面に出す（`SC-20`）

## 5. 写真とBlob Storage（G-6）

### コンテナ構成

```
photos/                       ← 非公開コンテナ
  {missionSetId}/
    {visitId}/
      {photoId}.jpg
```

ルーム単位で分けるのは、**ルームごと消すときにプレフィックス指定で消せる**ため。

### アップロード

**APIを経由させない。** F1 の帯域とCPUを写真の転送に使うと、無料枠をすぐ食う。

1. 端末 → `POST /photos/upload-url` に `photoId` と `visitId` を送る
2. API が **書き込み専用・15分・単一Blob限定** の SAS URL を返す
3. 端末が Blob へ直接 PUT
4. 完了後、端末 → `PUT /photos/{photoId}` でメタを登録

> 手順4が失敗すると **Blobだけが残る**。これは掃除の対象（下記）。
> 逆に手順3が失敗して4だけ通ることは無い（順序を守るため）。

### 読み取り

コンテナは非公開のまま、**読み取り専用SAS（1時間）** を付けたURLを一覧APIが返す。
URLが漏れても1時間で切れる。

### 圧縮

端末側で **長辺1600px / JPEG 品質0.8** に縮小してから上げる（実装済み）。
1枚あたり200〜400KB程度に収まり、写真300枚でも100MB前後。

### 孤児Blobの掃除

`Photo` の行が無いのに Blob だけ残る状態は、以下で起きる。

- メタ登録（手順4）の前にアプリが落ちた
- 記録リセットやルーム削除でDBだけ消えた

対策を2段構えにする。

1. **削除時にAPIがBlobも消す** — 通常はこれで足りる
2. **定期的な掃除** — `Photo` に無い Blob のうち、**作成から24時間以上経ったもの**を消す。
   Azure Functions のタイマートリガー（無料枠内）で月1回動かせば十分

## 6. エラーの形式

```jsonc
{ "error": "turn_in_progress",
  "message": "他の端末がサイコロを振っている最中です",
  "detail": { "turnId": "…" } }
```

| 状態 | 意味 | クライアントの動き |
|---|---|---|
| `400` | 入力が不正 | 直せる場合のみ表示。それ以外はキューから捨ててログ |
| `401` | トークンが無効 | 再参加を促す |
| `403` | 権限がない（他人の写真を消そうとした等） | 表示して終わり |
| `409 turn_in_progress` | 進行中ターンが既にある | **相手の進行を取り込んで画面を合わせる** |
| `409 rules_locked` | プレイ開始後に区間を変えようとした | 設定画面で理由を表示 |
| `409 display_name_taken` | 表示名の重複 | 入力し直させる |
| `5xx` / タイムアウト | サーバーが寝ている等 | **キューに残して後で再送。プレイは続ける** |

## 7. Q-02（誰がサイコロを振るか）への備え

**結論から言うと、どちらに転んでも作るものはほとんど変わらない。**

| 方式 | 追加で必要なもの |
|---|---|
| ① その場の代表が1台で操作 | **なし**。他のメンバーは記録を見るだけ |
| ② 全員の画面が同期する | `GET /state` の**定期取得（30秒間隔＋画面復帰時）** |

②でもリアルタイム通信は要らない。理由は3つ。

- 歩いている最中の更新頻度は数分に1回で、秒単位の同期が要らない
- **二重にサイコロを振ることはサーバー側で既に防げている**（`UX_Turn_Active` により2人目は 409）
- SignalR Service は別料金で、無料構成が崩れる

つまり **Q-02 は「排他されたときに画面でどう見せるか」というUIの問題に縮む**。
API設計を止める理由にはならないので、フェーズ2はこのまま進めてよい。

プッシュ通知（他の人の進行を知らせる）は、②を選び、かつ
「離れて歩く」運用をする場合にだけ必要になる。その時点で APNs を検討する。

### 手順6（写真）— 完了（2026-07-26）

`Endpoints/PhotoEndpoints.cs` と `Storage/`（`IPhotoStorage` / `BlobPhotoStorage`）。
接続文字列は **App Service の `ConnectionStrings__Storage`**、ローカルは
**user-secrets の `ConnectionStrings:Storage`**（`Storage:PhotoContainer` = `photos`）。
設定が無いときは起動を妨げず、写真のエンドポイントだけ `503 storage_unavailable` を返す。

| 決めたこと | 理由 |
|---|---|
| SASは**単一Blob限定** (`sr=b`)。書き込み `sp=cw` 15分 / 読み取り `sp=r` 1時間 | コンテナ単位や長期のSASを配ると、1枚上げる権限が「ルーム全体の鍵」になる |
| SASの開始を**5分さかのぼらせる** | 端末の時計が少し進んでいるだけで弾かれるのを防ぐ |
| `Photo.BlobUrl` には**署名なしのパス**を入れる | 署名付きURLを保存すると期限切れで使えなくなる。SASは都度発行する |
| 削除は**Blob → 行**の順 | 逆にすると、誰も辿れない孤児Blobが残る（やり直しが効かない） |
| リセット（`DELETE /progress`）は**プレフィックスでBlobごと消す** | 行はCASCADEで消えるが実体は残る |
| 写真は**チーム全員に見せる**（お題と違い伏せない） | 一緒に歩いた記録なので、隠す理由がない |

**実物のAzureに対して1往復を確認済み**（SAS発行 → BlobへPUT `201` → メタ登録 `204`
→ 一覧の読み取りURLで取得 `200`・**内容が一致** → 削除 `204` → 読み取り `404`）。

> 将来的にはアカウントキーをやめ、マネージドIDのユーザー委任SASに寄せる（`03_Azure構成と料金.md` §0）。
> 切り替え地点は `BlobPhotoStorage.Sas()` の1か所。

| 決めたこと | 理由 |
|---|---|
| 同じ対象への未送信は**最新の1件にまとめる**（`targetKey` で置き換え） | 着地 → ミッション → 効果 と同じターンへ何度もPUTするため。溜めると圏外復帰時に古い内容まで送り直す |
| ただし**最初に積んだ時刻は引き継ぐ** | 順序は「操作した順」でなければならない。ターンより先に訪問が届くと、まだ無いターンに紐づけようとして弾かれる |
| **1件でも再送すべき失敗が出たら、そこで止める** | 飛ばして次を送ると、あとから古い状態が上書きする |
| `400` は**捨てる**。`401` と `5xx` は残す | 何度送っても同じ失敗を残すとキューが永久に詰まり、以降の記録が一切送れなくなる。401 は再参加すれば通る |
| 取り込みは**足すだけ**。ローカルにしかない記録は消さない | 未送信のものが消えると、歩いた事実そのものが失われる |
| マスタの取り込みで**座標は上書きしない** | 現地で実測して直した値を、サーバーの概値で潰さないため |
| 送信の中身は駅の**サーバーID**。参加時に `/courses` で埋める | 同梱マスタには `serverId` が無い（フェーズ1はローカル完結だったため） |
