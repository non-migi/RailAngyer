# RailAngyer データ設計

> ⚠️ **この文書は ver.1（初期案）です。**
> 可変ルール（区間の自由設定・最大出目1〜9・ミッション効果・戻る／ジャンプ）に対応した
> **ver.2 の確定版は `07_データモデル仕様.html` と `06_schema.sql`** を参照してください。
> ver.2 では `Turn`（手番）テーブルが追加され、`Visit` の構造が変わっています。
> 本書は「なぜ共有DBが要るのか」「どういう考え方で分けたのか」を残すための文書として維持します。

> Azure SQL Database を前提としたテーブル設計。身内数人・小規模を想定。
> 写真の実体は Blob Storage に保存し、DBにはパス（URL）のみ持つ。

---

## 1. 全体像

共有が必要なデータ（ミッション・予定・記録・写真メタ）はすべてサーバー側DBに置く。
駅の座標などの固定データは、DBに持たずアプリ内に埋め込んでもよい（変わらないため）。ただし将来コースを増やすことを考えると、DB化しておくと追加が楽。

```
Course (コース: 南北線, 山手線 …)
  └─ Station (駅: 麻生, 大通 …)
MissionSet (ミッションセット / ルーム)
  ├─ Member (参加メンバー)
  ├─ Mission (ミッション: 駅ごとに1メンバー1個まで)
  ├─ Schedule (予定)
  └─ Visit (訪問記録: チームのコマの足あと。全訪問駅ぶん)
        └─ Photo (写真メタ)
```

## 2. テーブル定義

### 2.1 Course（コース）
将来の路線追加に対応するマスタ。

| カラム | 型 | 説明 |
|---|---|---|
| CourseId | INT (PK, IDENTITY) | コースID |
| Name | NVARCHAR(50) | 「南北線」「山手線」など |
| LineColor | NVARCHAR(9) | 路線カラー(#RRGGBB) |
| CreatedAt | DATETIME2 | 作成日時 |

### 2.2 Station（駅）
コースに属する駅マスタ。

| カラム | 型 | 説明 |
|---|---|---|
| StationId | INT (PK, IDENTITY) | 駅ID |
| CourseId | INT (FK→Course) | 所属コース |
| Name | NVARCHAR(50) | 駅名 |
| OrderNo | INT | コース内の並び順（始点=1） |
| Latitude | FLOAT | 緯度 |
| Longitude | FLOAT | 経度 |

### 2.3 MissionSet（ミッションセット / ルーム）
「誰と誰で遊ぶか」の単位。共有の器。

| カラム | 型 | 説明 |
|---|---|---|
| MissionSetId | UNIQUEIDENTIFIER (PK) | セットID |
| CourseId | INT (FK→Course) | 対象コース |
| Name | NVARCHAR(100) | 「夏の南北線ツアー」など |
| InviteCode | NVARCHAR(10) | 招待コード（メンバー参加用） |
| CreatedBy | UNIQUEIDENTIFIER | 作成者(MemberId) |
| CreatedAt | DATETIME2 | 作成日時 |

### 2.4 Member（メンバー）
セットに参加する身内。厳密なアカウントは持たず軽く識別。

| カラム | 型 | 説明 |
|---|---|---|
| MemberId | UNIQUEIDENTIFIER (PK) | メンバーID |
| MissionSetId | UNIQUEIDENTIFIER (FK) | 所属セット |
| DisplayName | NVARCHAR(50) | 表示名 |
| JoinedAt | DATETIME2 | 参加日時 |

### 2.5 Mission（ミッション）
**駅ごとに、1メンバーにつき1個まで**（0個でもよい）。UNIQUE制約で担保。

| カラム | 型 | 説明 |
|---|---|---|
| MissionId | UNIQUEIDENTIFIER (PK) | ミッションID |
| MissionSetId | UNIQUEIDENTIFIER (FK) | 所属セット |
| MemberId | UNIQUEIDENTIFIER (FK) | 作成者 |
| StationId | INT (FK→Station) | 対象駅（**必須**） |
| Content | NVARCHAR(300) | ミッション内容（お題テキスト） |
| CreatedAt | DATETIME2 | 作成日時 |

> 制約: `UNIQUE(MissionSetId, MemberId, StationId)` … 「1人1駅につき1個まで」を保証。
> 作らない駅にはレコードを作らない（＝その駅のミッションは0個になりうる）。
> サイコロの目は「進む駅数」であり、ミッションとは無関係のため `DiceFace` 列は持たない。

### 2.6 Schedule（予定）
プレイ日時・集合場所の共有。

| カラム | 型 | 説明 |
|---|---|---|
| ScheduleId | UNIQUEIDENTIFIER (PK) | 予定ID |
| MissionSetId | UNIQUEIDENTIFIER (FK) | 所属セット |
| Title | NVARCHAR(100) | 「7/30 南北線チャレンジ」など |
| StartAt | DATETIME2 | 開始日時 |
| MeetPlace | NVARCHAR(100) | 集合場所 |
| CreatedBy | UNIQUEIDENTIFIER | 作成者 |

### 2.7 ScheduleAttendee（参加可否）
予定への出欠。

| カラム | 型 | 説明 |
|---|---|---|
| ScheduleId | UNIQUEIDENTIFIER (FK, PK複合) | 予定ID |
| MemberId | UNIQUEIDENTIFIER (FK, PK複合) | メンバー |
| Status | TINYINT | 0=未定,1=参加,2=不参加 |

### 2.8 Visit（訪問記録）
チームのコマがどの駅にいつ到達したか。**チームで1つのコマを進めるため、メンバー単位ではなくセット単位で記録する。**
着地駅（ミッション実施駅）だけでなく、**途中で訪れた駅もすべて1行ずつ記録する**。

| カラム | 型 | 説明 |
|---|---|---|
| VisitId | UNIQUEIDENTIFIER (PK) | 訪問ID |
| MissionSetId | UNIQUEIDENTIFIER (FK) | 所属セット |
| StationId | INT (FK→Station) | 到着した駅 |
| ArrivedAt | DATETIME2 | 到着日時 |
| IsLanding | BIT | **着地駅か**（1=サイコロの目の着地点、0=途中で訪れただけ） |
| DiceValue | TINYINT (NULL可) | この区間で振った目＝進んだ駅数（着地駅の行にのみ入れる） |
| SelectedMissionId | UNIQUEIDENTIFIER (NULL可) | 抽選で当たったミッション（着地駅のみ。0個だったらNULL） |
| MissionDone | BIT | ミッション達成フラグ（着地駅のみ） |

> 制約: `UNIQUE(MissionSetId, StationId)` … 同じ駅を二度記録しない（コースを一方向に進む前提）。
> **現在位置** は別テーブルを持たず、`Visit` から導出する:
> 「`IsLanding=1` の中で `Station.OrderNo` が最大の駅」＝いまコマがいる駅。

### 2.9 Photo（写真メタ）
実体は Blob Storage。DBはパスのみ。訪れた駅で撮れるなら撮る（着地駅・途中駅とも可、任意）。
**同じ訪問に対して複数メンバーが複数枚**撮れる。

| カラム | 型 | 説明 |
|---|---|---|
| PhotoId | UNIQUEIDENTIFIER (PK) | 写真ID |
| VisitId | UNIQUEIDENTIFIER (FK→Visit) | どの駅の訪問で撮ったか |
| MemberId | UNIQUEIDENTIFIER (FK→Member) | 撮影者 |
| BlobUrl | NVARCHAR(500) | Blob Storage上のURL |
| TakenAt | DATETIME2 | 撮影日時 |

## 3. プレイ1ターンのデータの流れ

サイコロを振ってから次にサイコロを振るまでが1ターン。

1. **サイコロを振る** → 出目 N。現在位置の `OrderNo` + N が着地駅（コース終端を超えたら終端＝ゴール）
2. **1駅ずつ歩く** → 到達するたび `Visit` を1行 INSERT（`IsLanding=0`）。写真を撮ったら `Photo` を INSERT
3. **着地駅に到達** → `Visit` を INSERT（`IsLanding=1`, `DiceValue=N`）
4. **着地駅のミッション群を取得**
   `SELECT * FROM Mission WHERE MissionSetId=@set AND StationId=@station`
   - 1件以上 → クライアント側で乱数抽選し1件を選ぶ
   - **0件 → ミッションなし。すぐ 1 に戻る**（企画書 §7 の暫定方針）
5. 選んだミッションIDを `Visit.SelectedMissionId` に、達成したら `MissionDone=1` を保存
6. 1 に戻る。着地駅がコース終端ならクリア

サーバーで抽選ロジックを持つ必要はなく、DBは単純なテーブルで足りる。

---

## 4. 写真の扱い

- 写真の**実体（画像バイナリ）はDBに入れない**。Azure Blob Storage に保存する。
- DBには Blob のURLだけを持つ（Photo.BlobUrl）。
- 理由: DBに画像を入れるとサイズが膨れ、無料枠のストレージをすぐ食う。Blobの方が安く適切。

---

## 5. インデックスの目安（小規模なので最小限）

- `Mission(MissionSetId, StationId)` … 着地時の抽選取得用
- `Visit(MissionSetId, StationId)` … 記録一覧・現在位置の導出用（UNIQUE制約が兼ねる）
- `Station(CourseId, OrderNo)` … 盤面表示の並び順・現在位置の算出用

身内数人・レコード数百〜数千規模なので、複雑なチューニングは不要。
