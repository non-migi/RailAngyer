## フェーズ1: ローカルMVP（共有なし）

### 目的

**リリース候補を作ることではなく、最も不確実な部分を最小コストで確かめること。**
以下はいずれもサーバーとは無関係で、ここが破綻していたらAPIを作っても意味がない。

| 検証項目 | 合格条件 | 失敗したときの影響 |
|---|---|---|
| **駅座標の精度と150m判定** | 全16駅で、駅前に立ったときに自動で到着になる | 毎回手動到着を押すことになり、ゲームが成立しない |
| 1駅ずつ歩くテンポ | 出目6（約5〜8km）が現実的に歩けるか | 最大出目の既定値を6より小さくする必要がある |
| バッテリー消費 | 半日（4〜5時間）の連続使用に耐える | 測位方式を見直す（常時測位→ジオフェンス主体へ） |
| 中断・復帰 | 移動中にアプリを落としても同じ画面に戻る | 実地で進行不能になる |

### 作るもの

- [x] SwiftData モデルの定義（`10_アプリ設計.md` §3）
- [x] 南北線16駅のマスタ同梱と投入（座標は概値。現地で更新する）
- [x] **`GameEngine` とユニットテスト（`10_アプリ設計.md` §4 の12ケース）**
- [x] すごろく盤 / 路線図（訪問駅と**着地駅**を区別。区間を反映）
- [x] 区間（スタート駅・ゴール駅）と最大出目（1〜9）の設定 — 端末内の設定
- [x] サイコロ → 着地駅の告知（進む向きの判定・ゴールでのクランプ）
- [x] GPS到着判定（半径150m）— 途中駅も含め訪れた駅すべてを記録
      ／ 精度100m超の測位は不採用 ／ 到着したら監視を次の駅へ張り替え
- [x] **地図**（現在地・次の駅・**到着判定の円**）と、純正マップへの経路の受け渡し
      ※ 円を描くのは、現地で判定が合わないとき「座標のズレか測位の悪さか」を切り分けるため
- [x] **徒歩経路の表示**（`MKDirections`）— 経路の線・実距離・所要時間。
      取得に失敗したら直線距離に落として進行を止めない
- [x] **到着のローカル通知** — バックグラウンドのときだけ。
      これが無いとバックグラウンド監視の意味が薄い（画面を見続ける前提になってしまう）
- [x] 着地駅でミッション抽選・達成 → 効果の適用 → 次のサイコロへ
- [x] 達成率表示（踏破率は重複を除いて数える）
- [x] 写真撮影 → 駅に紐づけ（端末ローカル保存。長辺1600pxに縮小して保存）
      ／ 通り道の駅でも**到着の一拍を置いて撮れる**ようにした
- [x] 駅詳細（SC-18）— 訪問ごとの記録・写真・ミッションの結果
- [x] 中断・復帰処理（`10_アプリ設計.md` §5.3）

> テストは 64 件（コア34 / モデル・進行27 / UIテスト3）。
> UIテストはシミュレータの現在地を動かして「歩かせて」検証しており、
> **半径の外では到着せず、駅に入ると自動で到着する**こと、
> **移動中に強制終了しても同じ画面に戻る**ことを確認済み。

## リスク・注意点

- **GPS精度**: 駅座標は概値。現地で数十m単位のズレが出る駅は要微調整。
- **無料枠の上限**: Azure無料オファーの条件変更に注意。上限到達時の挙動を「自動停止」に設定しておくと課金事故を防げる。
- **認証の軽さと安全性**: 招待コードは手軽だが、コードが漏れると誰でも入れる。身内用なら許容範囲。
- **写真容量**: 枚数が増えるとBlobの容量・転送が増える。当面は問題にならない規模。
- **App Store審査**: 位置情報の利用目的、UGC（ユーザー投稿=写真・ミッション文）の扱いに配慮。過去のjankenアプリの審査経験が活きる。
