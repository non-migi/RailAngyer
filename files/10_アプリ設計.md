# RailAngyer アプリ設計

> iOS / SwiftUI / SwiftData。フェーズ1（ローカルMVP）を実装するための設計。
> 画面の中身は `08_画面仕様.html`、ルールは `05_フロー仕様.html`、
> サーバー側は `06_schema.sql` / `07_データモデル仕様.html` を参照。
> 作成日: 2026-07-25

---

## 1. 方針

| ID | 方針 | 理由 |
|---|---|---|
| AD-01 | **ローカルモデルはサーバーのテーブルとほぼ1対1にする** | フェーズ2の同期を「行を送るだけ」に単純化できる。構造がずれると変換層が要る |
| AD-02 | **フェーズ1でも `MissionSet` / `Member` を作る** | ローカル限定でも「ルーム1件・メンバー1人」として持てば、フェーズ2で構造が変わらない。区間と最大出目の置き場所にもなる |
| AD-03 | **ルールの計算はDBにも位置情報にも依存させない** | `GameEngine` を純粋な構造体にすることで、**シミュレータも実機もGPSも使わずにユニットテストできる**。着地駅の算出・クランプ・効果適用がここに集まる |
| AD-04 | **ローカルの主キーは UUID** | サーバーの `MissionSet` 系はもともと UUID。マスタ系（INT）だけ `serverId` を別に持つ |
| AD-05 | **写真の実体はフェーズ1では端末ローカル** | `Photo.blobUrl` はフェーズ2で埋める。ローカルのファイル名と併存させる |
| AD-06 | **状態は保存せず、常に `Turn` から導出する** | サーバー側の設計（D-01）と揃える。二重管理をしない |

## 3. SwiftData モデル定義

### 3.1 型の対応

| Azure SQL | Swift | 備考 |
|---|---|---|
| `UNIQUEIDENTIFIER` | `UUID` | そのまま共有できる |
| `INT`（マスタのID） | `Int`（`serverId`） | ローカルの主キーとは別に持つ |
| `TINYINT` | `Int` | `UInt8` にはしない。演算で毎回キャストが要るため |
| `BIT` | `Bool` | |
| `NVARCHAR` | `String` | |
| `DATETIME2` | `Date` | **UTCで保持**。表示時のみローカル時刻へ |
| `FLOAT` | `Double` | 緯度経度 |
| 区分値 | `Int` ＋ 計算プロパティで `enum` | SwiftDataの移行に強い形にする |

### 3.2 区分値

```swift
enum EffectType: Int, CaseIterable, Codable {
    case none = 0        // 効果なし（通常のお題）
    case forward = 1     // 進む（EffectValue 駅）
    case back = 2        // 戻る（EffectValue 駅）
    case rollAgain = 3   // もう一度振る
    case jump = 4        // 指定駅へ移動
}

enum VisitKind: Int, Codable {
    case start = 0          // 始点
    case passing = 1        // 通り道
    case landing = 2        // 着地（ミッションを引く）
    case effectPassing = 3  // 効果による移動の通り道
    case effectArrival = 4  // 効果による移動の到達点
}

enum SyncState: Int, Codable {
    case localOnly = 0   // まだサーバーに送っていない
    case synced = 1
    case pendingUpdate = 2
}
```

### 3.3 マスタ

```swift
import SwiftData

@Model final class Course {
    var id: UUID = UUID()
    var serverId: Int?              // Azure の CourseId
    var name: String = ""
    var lineColorHex: String?

    @Relationship(deleteRule: .cascade, inverse: \Station.course)
    var stations: [Station] = []

    init(name: String, lineColorHex: String? = nil) {
        self.name = name; self.lineColorHex = lineColorHex
    }
}

@Model final class Station {
    var id: UUID = UUID()
    var serverId: Int?              // Azure の StationId
    var name: String = ""
    var orderNo: Int = 0            // 路線の端からの通し番号。位置計算はすべてこの値
    var latitude: Double = 0
    var longitude: Double = 0
    var course: Course?

    init(name: String, orderNo: Int, latitude: Double, longitude: Double) {
        self.name = name; self.orderNo = orderNo
        self.latitude = latitude; self.longitude = longitude
    }
}
```

> マスタはアプリに同梱した JSON から初回起動時に投入する。
> 札幌3路線は国土数値情報 N02-22（JGD2011）の駅区間中央へ補正済み。
> 地下出入口との距離は実地で確認し、必要な駅だけ追加補正する。

### 3.4 ルーム

```swift
@Model final class MissionSet {          // UI上の呼称は「ルーム」
    var id: UUID = UUID()                // サーバーの MissionSetId と同一
    var name: String = ""

    var diceMax: Int = 6                 // 1〜9

    @Relationship(deleteRule: .cascade, inverse: \Turn.missionSet)    var turns: [Turn] = []

    var id: UUID = UUID()

    var missionSet: MissionSet?

        self.displayName = displayName; self.isMe = isMe
    }
}

@Model final class Mission {
    var id: UUID = UUID()
    var content: String = ""
    var effectTypeRaw: Int = EffectType.none.rawValue
    var effectValue: Int?                // 進む・戻るの駅数
    var createdAt: Date = Date()
    var syncState: Int = SyncState.localOnly.rawValue

    var missionSet: MissionSet?
    var member: Member?
    var station: Station?

```

> **サーバー側の CHECK 制約（CK-06 / CK-07）はローカルには無い。**
> 「効果なしなのに駅数が入っている」といった不整合は、
> 保存前に `Mission.validate()` で弾く。フェーズ2で送信したときに拒否されるより早く気づける。

## 4. ルール計算（GameEngine）

**位置情報にもDBにも依存しない純粋な構造体にする。** ここだけでルールのテストが完結する。

```swift
struct GameEngine {
    let startOrder: Int
    let goalOrder: Int
    let diceMax: Int

    /// 進む向き。+1 = OrderNo が増える / -1 = 減る
    var direction: Int { goalOrder > startOrder ? 1 : -1 }

    /// 区間内の OrderNo の範囲
    var range: ClosedRange<Int> {
        min(startOrder, goalOrder)...max(startOrder, goalOrder)
    }

    func roll() -> Int { Int.random(in: 1...diceMax) }

    /// 出目による着地駅。ゴールを超えたらゴールで止める（R-11）
    func landingOrder(from current: Int, dice: Int) -> Int {
        clampToGoal(current + direction * dice)
    }

    /// 効果を適用した後の終了位置（R-11 / R-12）
    func endOrder(landing: Int, effect: EffectType,
                  value: Int?, jumpTo: Int?) -> Int {
        switch effect {
        case .none, .rollAgain: return landing
        case .forward:          return clampToGoal(landing + direction * (value ?? 0))
        case .back:             return clampToStart(landing - direction * (value ?? 0))
        case .jump:             return (jumpTo.map { range.contains($0) ? $0 : landing }) ?? landing
        }
    }

    /// 歩く順に並べた駅（最後が目的地）。出目1・効果1駅なら1件だけ返る
    func path(from: Int, to: Int) -> [Int] {
        guard from != to else { return [] }
        let step = to > from ? 1 : -1
        return stride(from: from + step, through: to, by: step).map { $0 }
    }

    func isCleared(_ order: Int) -> Bool { order == goalOrder }

    private func clampToGoal(_ o: Int) -> Int {
        direction == 1 ? Swift.min(o, goalOrder) : Swift.max(o, goalOrder)
    }
    private func clampToStart(_ o: Int) -> Int {
        direction == 1 ? Swift.max(o, startOrder) : Swift.min(o, startOrder)
    }
}
```

### テストで必ず確認すること

| # | ケース | 期待 |
|---|---|---|
| 1 | 麻生(1)→真駒内(16)、現在6、出目3 | 着地9 |
| 2 | 同上、現在12、出目5 | **着地16（超過分は切り捨て）** |
| 3 | **逆走**（16→1）、現在12、出目3 | 着地9 |
| 4 | 逆走、現在3、出目5 | **着地1** |
| 5 | 区間6→11、現在10、出目3 | **着地11** |
| 6 | 着地10で「戻る3」、区間6→11 | 終了7 |
| 7 | 着地7で「戻る5」、区間6→11 | **終了6（スタートでクランプ）** |
| 8 | 着地9で「進む4」、区間6→11 | **終了11（ゴールでクランプ）** |
| 9 | ジャンプ先が区間外(3)、区間6→11 | **移動しない（着地のまま）** |
| 10 | `path(from:6,to:9)` | `[7,8,9]` |

## 5. 状態管理

### 5.1 画面フェーズ

`05_フロー仕様.html` の ST-1〜ST-8 に対応させる。

```swift
enum GamePhase: Equatable {
    case setup                                  // ST-1 準備中
    case waiting(current: Int)                  // ST-2 待機（サイコロを振れる）
    case moving(turn: UUID, next: Int, remaining: Int)  // ST-3 移動中
    case landed(turn: UUID, station: Int)       // ST-4 着地（抽選前）
    case mission(turn: UUID, mission: UUID)     // ST-5 ミッション実行中
    case effect(turn: UUID, to: Int)            // ST-6/ST-3' 効果による移動
    case cleared                                // ST-8 クリア
}
```

### 5.2 現在位置の導出（AD-06）

```swift
var currentOrder: Int {
    let completed = missionSet.turns
        .filter { $0.completedAt != nil }
        .max { $0.turnNo < $1.turnNo }
    return completed?.endStation?.orderNo
        ?? missionSet.startStation?.orderNo ?? 1
}
```

**`OrderNo` の最大値ではなく「最後に完了したターン」を見る。** 戻る効果があるため（ver.2 の変更点）。

### 5.3 起動時の復元（CM-06 / E-05）

進行中の `Turn`（`endStation == nil`）を1件探し、その中身から画面を決める。

| 進行中Turn | `arrivedAt` | `selectedMission` | 判定 | 復帰先 |
|---|---|---|---|---|
| なし | — | — | 待機 | SC-04 盤面 |
| あり | nil | — | 着地駅へ移動中 | SC-07 ナビ（次の目標は下記で算出） |
| あり | あり | nil | 着地済み・抽選前 | SC-09 ミッション（0件なら効果適用へ） |
| あり | あり | あり（`endStation` nil） | 効果適用前 | SC-21 効果の適用 |

移動中の「次に行くべき駅」は、`path` と訪問済みの差分で求める。

```swift
let planned = engine.path(from: turn.fromStation!.orderNo,
                          to: turn.landingStation!.orderNo)
let visited = Set(turn.visits.compactMap { $0.station?.orderNo })
let next = planned.first { !visited.contains($0) }   // nil なら着地済み
```

> **`Turn` を振った時点で保存する**ので、アプリを落としても出目と行き先が残る。
> これが ver.1 で積み残していた T-01 の解決。

### 5.4 1ターンの書き込み手順

`05_フロー仕様.html` の F-01〜F-11 に対応。**それぞれの直後に `context.save()` する**（途中で落ちても復元できるようにするため）。

1. `Turn` を作成（`endStation` は nil）→ 保存
2. 通り道の駅に着くたび `Visit(.passing)` → 保存
3. 着地駅で `Visit(.landing)` ＋ `Turn.arrivedAt` → 保存
4. 抽選 → `Turn.selectedMission` → 保存
5. 達成／未達成 → `Turn.missionDone` → 保存
6. 効果で移動するなら `Visit(.effectPassing / .effectArrival)` → 保存
7. `Turn.endStation` ＋ `completedAt` → 保存（**ここで進行中でなくなる**）

## 6. 位置判定の詳細設計

### 6.1 パラメータ

| 項目 | 値 | 根拠 |
|---|---|---|
| 到着半径 | **150 m**（設定で変更可） | R-01。座標が概値のうちは調整が要る |
| 精度の足切り | `horizontalAccuracy` **> 100 m は無視** | 精度の悪い測位で誤到着させない |
| `desiredAccuracy` | `kCLLocationAccuracyNearestTenMeters` | `Best` はバッテリーを食う。10m精度で足りる |
| `distanceFilter` | **20 m** | 更新頻度を抑える |
| 監視対象 | **常に1駅だけ** | R-02。先の駅の圏内に入っても到着にしない |

### 6.2 到着判定

```swift
func shouldArrive(at station: Station, location: CLLocation) -> Bool {
    guard location.horizontalAccuracy > 0,
          location.horizontalAccuracy <= 100 else { return false }
    let target = CLLocation(latitude: station.latitude, longitude: station.longitude)
    return location.distance(from: target) <= arrivalRadius
}
```

### 6.3 チャタリング対策（E-04）

150m の境界を出入りすると、同じ駅で何度も到着イベントが起きる。

**対策: 到着したら即座に監視対象を次の駅へ進める。**
到着済みの駅は、そのターンの間は判定対象に戻さない。

```swift
// 到着処理は「1回だけ」通す
guard !arrivedOrdersInThisTurn.contains(station.orderNo) else { return }
arrivedOrdersInThisTurn.insert(station.orderNo)
recordVisit(station)
advanceTarget()          // 監視を次の1駅へ張り替える
```

サーバー側は ver.2 で駅の一意制約を外したため、**DBでは重複を弾けない**（ver.1 との違い）。
アプリ側で確実に止める必要がある。

### 6.4 バックグラウンド動作

歩いている間ずっと画面を見ているとは限らない。

- **ジオフェンス（`CLCircularRegion`）を1件だけ張り、到着のたびに次の駅へ張り替える**
- iOS の同時監視上限は20件だが、**常に1件しか使わないので上限は問題にならない**
  （`05_フロー仕様.html` の T-02 で「20駅を超えると絞る必要がある」と書いたが、この方式なら不要）
- 到着時にローカル通知を出し、アプリを開かせる
- `UIBackgroundModes: location` が必要

### 6.5 測位できないとき（E-01）

地下鉄沿線・地下駅では測位が不安定になる。

- 精度が悪い状態が続いたら、**ナビ画面に「電波が悪いようです」を表示**
- **[到着した] の手動ボタンを常に置く**（隠さない）。地下駅では主要な手段になる想定
- 位置情報の権限が拒否されている場合は、起動時に用途を説明して再要求。それでも拒否なら手動モードで進行

### 6.6 到着の通知

**歩いている間ずっと画面を見ているとは限らない。**
ジオフェンスで到着を検知しても、知らせる手段が無ければ気づけないため、ローカル通知を出す。

| 項目 | 仕様 |
|---|---|
| 種類 | **ローカル通知のみ**（`UNUserNotificationCenter`）。サーバー不要 |
| 出す条件 | **アプリがバックグラウンドのときだけ**。画面を見ているのに二重に知らせても邪魔になる |
| 出す場面 | 通り道の駅に到着／着地駅に到着（ミッション数を添える）／ゴール |
| 出さない場面 | **手動で到着させたとき**。画面を見ているのが自明のため |
| 権限 | 位置情報の許可と同じタイミングで要求する |

> プッシュ通知（他の端末の進行、予定のリマインド）は **Q-02（誰がサイコロを振るか）が決まるまで判断しない**。
> 必要になれば APNs の設定と有料の Apple Developer Program が要る。

### 6.7 徒歩経路の表示

`MKDirections` で次の駅までの徒歩経路を取り、地図に線を描く。

| できること | できないこと |
|---|---|
| 経路の線を描く（`MapPolyline`） | 音声案内 |
| **実際に歩く距離**と所要時間を出す（直線距離ではない） | 経路を外れたときの自動リルート |
| 最初の曲がり角の指示を出す | 純正マップのような案内画面 |

- 取得は**通信が要る**。地下・圏外では取れないため、**失敗したら直線距離の表示に落として進行を続ける**
- 取り直すのは「目的の駅が変わったとき」と「出発地点から400m以上離れたとき」だけ。毎回の測位では取り直さない
- 込み入った場所では「マップで開く」で純正マップに渡す。この逃げ道は残す

### 6.8 必要な Info.plist キー

| キー | 用途 |
|---|---|
| `NSLocationWhenInUseUsageDescription` | 「駅への到着を判定するために現在地を使います」 |
| `NSLocationAlwaysAndWhenInUseUsageDescription` | 画面を見ていない間も到着を検知するため |
| `UIBackgroundModes` = `location` | バックグラウンドでの測位 |
| `NSCameraUsageDescription` | 駅での撮影 |
| `NSPhotoLibraryAddUsageDescription` | 撮った写真の保存 |

### 7.4 UIテストによる自動検証（実装済み）

GPX の手動再生に加えて、**到着判定を自動で検証する UIテスト**を用意した
（`RailAngyerApp/UITests/ArrivalUITests.swift`）。

`XCUIDevice.shared.location` でシミュレータの現在地を動かし、実際に「歩かせて」確かめる。

| テスト | 内容 |
|---|---|
| `testWalkingIntoRadiusTriggersArrival` | 麻生から北34条へ。**約300m手前では到着せず**、駅に入ると**自動で到着になる** |
| `testManualArrivalWorks` | 位置情報に頼らず手動ボタンでも進めること（E-01） |

出目は環境変数 `RAILANGYER_FIXED_DICE` で1に固定し、行き先を一意にしている。
`RAILANGYER_IN_MEMORY=1` でストアをメモリ上にし、毎回まっさらな状態から始める
（`Sources/Game/TestHooks.swift`）。通常の起動では環境変数が無いため影響しない。

```bash
tools/prepare-simulator.sh "iPhone 17 Pro"   # 先に位置情報の許可を与える
xcodebuild -project RailAngyerApp/RailAngyerApp.xcodeproj -scheme RailAngyerApp \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test
```

> **UIテストの前に `tools/prepare-simulator.sh` を実行する。**
> 新しいシミュレータでは位置情報が未許可で、許可ダイアログが操作を塞ぐため、
> 位置情報を使うテストが落ちる。
> ダイアログをテスト内で閉じる方法（springboard のボタンを叩く）は取りこぼしがあったので、
> **事前に `simctl privacy` で付与する方式にしている**。
>
> Xcode が更新されるとシミュレータのランタイムが入れ替わり、
> **デバイスが作り直されて権限がリセットされる**点に注意。
> 実際に 2026-07-26 に Xcode 26.4.1 → 26.6 の更新でこれが起きた。

### 7.5 シミュレータで確認できないこと

- **バックグラウンドでのジオフェンス通知** — 挙動が実機と異なる。実機で確認する
- **測位精度の劣化** — 常に高精度で返るため、地下での不安定さは再現できない
- **バッテリー消費**

**実機テストは、座標の実測とセットで行う。** 現地で各駅の実際の座標を記録し、マスタを更新する（E-02 / T-03）。

## ふりかえりの集計（SC-17）

`Sources/Game/JourneySummary.swift`。**画面から切り離した値**にしてある。
見た目より先に「何をどう数えるか」を決めないと、踏破率のように数え方でぶれるため。

| 数えるもの | 決めごと |
|---|---|
| 踏破 | 一度でも訪れた駅の数。**再訪は重複して数えない**（DV-06） |
| 訪問回数 | 駅ごとの記録では再訪も数える（「3回来た」は見せたい情報） |
| 着地 | 着地した駅の数。ミッションを引いた駅 |
| 合計時間 | 最初にサイコロを振ってから最後の記録まで。進行中は現在まで |
| 移動時間 | 駅間の区間時間の合計。効果による移動も含む |
| ミッション時間 | 着地してからターンを完了するまで |
| その他 | 合計から移動とミッションを引いた時間（休憩・待ち合わせなど） |
| 平均ペース | 駅間の直線距離合計 ÷ 移動時間（分/km） |
| お題 | 引いたお題を、ターン順に達成の可否つきで並べる |

- **クリア後だけでなく途中でも開ける。** 歩いている最中に「いまどれくらい？」を見たくなる
- 共有画像は `ImageRenderer` に**画面と同じカード**を描かせる。別々に作ると数字が食い違う
- 共有するのは数字と駅の並びで、写真は含めない（写真は各自の端末にある）

## 時間・ペースと地図の記録

`Sources/Game/WalkTiming.swift` と `RailAngyerCore/Pace.swift`。
新しい保存項目は増やさず、既存の `Turn.rolledAt` / `Turn.arrivedAt` /
`Turn.completedAt` / `Visit.arrivedAt` から後で集計し直す。

| 値 | 算出方法 |
|---|---|
| 区間時間 | 最初はサイコロ時刻→最初の到着、以降は前駅の到着→次駅の到着 |
| 区間距離 | 保存済み駅座標どうしのハーバサイン距離 |
| 区間ペース | 区間時間 ÷ 区間距離。`12分30秒/km` の形で表示 |
| 全体ペース | 全区間の距離合計 ÷ 移動時間合計 |
| ペース色 | 7〜20分/kmを、速い青→12分/km前後の緑→ゆっくりの赤へ連続補間 |

- 訪問時刻が直前の基準時刻より前なら、その記録は区間にも次の起点にも使わない
- 駅間は実経路ではなく**直線距離**なので、表示ペースは実際より遅め（数字が大きめ）になる
- 盤面では未通過を点線、通過済みを実線で描き、実線を分/kmに応じた連続色にする
- 色だけに頼らず、地図の凡例と各画面の分/kmを併記する
- `BoardView` は全体、`TurnFlowView` は今回、`StationDetailView` は訪問区間、
  `JourneySummaryView` と共有画像は全体内訳を表示する
- `TimingUITests` で盤面・駅詳細・ふりかえりを1ターン通して撮影し、地図凡例が
  下部ボタンや現在地表示と重ならないことを確認している
